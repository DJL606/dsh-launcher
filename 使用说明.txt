v0.6.7：一个出口 + 一处更新入口 + 启动环境净化 + 接口自检
---------------------------------------------------------
本轮起因是四个"用起来别扭/悄悄坏掉"的点，全部实修：

1) 托盘只留一个退出项
   旧版有两个："停止服务并退出"（只管本程序自己起的服务）和"结束 3080 服务
   并退出…"（只管别人的服务）。用户得先自己判断该点哪个，点错就会留下一个
   谁都不管的服务。现在合并成一个"停止服务并退出"：
     · 自己有服务在跑            → 直接停掉退出
     · 自己没有、3080 上有服务   → 问一次"结束它并退出？"（默认否）
     · 3080 上什么都没有         → 直接退出

2) 更新检查合并成一张勾选菜单（托盘"检查 dsh / 插件更新…"）
   启动后约 12 秒在后台自动检查；托盘入口随时手动检查。检查内容：
     · dsh 本体：npm latest 与当前版本比对
     · 每个 profile 的第三方插件：逐个查 npm latest
   有新版本才弹菜单，每项都可单独勾选（默认全选），点"更新选中项"逐个执行：
     · dsh 本体 → 后台下载，安装/启动失败自动回退（沿用 v0.6.4 起的既有机制）
     · 插件     → 文件级安装：npm pack 下载 → 解包 → 覆盖到 profile 的
                  node_modules（**先整目录备份**到 <profile>\.backup-update-<时间戳>\，
                  可回滚），不需要 pnpm，并同步 profile/package.json 里的版本号
   自动跳过、不参与更新的东西：
     · "link:"/"file:"/"workspace:" 规格的插件（本地开发包）
     · node_modules 里是符号链接/junction 的插件（指向本地开发检查点，
       比如 @yuxianglin/dsh-bridge-browser → dsh-browser）
   ★ 关键安全闸门：只提示**与当前 dsh 版本相容**的插件版本。
     实测例子：dsh-perm-gate 4.2.1 只声明支持 >=0.1.7-rc.1 <0.1.8-0，
     而本机 dsh 是 0.1.5-rc.3 —— 若照"有新版本就升"提示，一升级就会重演
     "插件在装载阶段抛错、整个 profile 起不来"。现在会被直接拦下并在
     "已是最新"提示里说明原因（依据 npm 上该版本的 engines.dsh 与
     peerDependencies 里所有 @deepseek-ai/dsh-* 约束）。

3) 启动环境净化（修一个会让 dsh 直接起不来的坑）
   实测：dsh 内部写配置时会删自己的 .lock 文件；如果启动器自身是从
   某些宿主环境里被拉起的，会继承一个 node 语言 shim
   （NODE_OPTIONS=--require ...node-language-shim.cjs），它带的 safe-delete
   守卫会拦下这次删除，dsh 立刻以
   `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] ... .credentials.yaml.lock`
   报错退出（或卡在 "timed out waiting for the writer lock"）。
   现在启动 dsh 前一律在命令行里 `set NODE_OPTIONS=` 与
   `set CODEBUDDY_SAFE_DELETE_BULK_GUARD=`，无论启动器从哪来都能正常起。
   顺带：锁文件残留（上次异常退出留下 .lock）也会导致同样的超时，
   处理办法就是删掉 %USERPROFILE%\.dsh\ 下的 .credentials.yaml.lock / settings.yaml.lock。

4) 服务接口自检（启动后 6 秒、只记日志 + 失败时一条气泡）
   用带 token 的地址换 cookie，再 POST 一个只读接口（agentPresets/list）。
   为什么要有这一步：服务"在跑"不等于"接口能用"。实测遇到过两类故障，
   现象都是页面能打开但按钮全废（Failed to fetch）：
     · 服务端没在跑（浏览器里是缓存页面）→ 现在启动器会自己拉起并自检
     · **页面里是旧版前端 bundle**（浏览器会话恢复出的旧标签页）→ 旧前端
       调用的接口在新版已改名（如 attachments/upload → fileUploads/upload），
       于是只有这些按钮坏。解法：关掉所有旧标签页重开（或 Ctrl+F5）。
   自检不通过时会在日志里留下明确记录，并弹一条气泡提示上面的处理办法。


v0.6.6：用"服务记录"替掉"比我早启动就是孤儿"的启发式
-----------------------------------------------------
问题（v0.6.4/v0.6.5 遗留）：判断 3080 上的服务是不是"别人留下的孤儿"，用的是
"监听进程比我启动得早"。它会把**本程序自己上一次启动的服务**也判成孤儿 ——
启动器一重启，服务自然比新进程早，于是每次重启都多弹一次"是否结束它"；
自检里 leftover_service 对一个完全健康的自有服务也报 True。

现在：本程序把服务启动成功后，把"这是我起的"写进状态文件：
    service_pid=<监听进程 PID>
    service_start=<该进程启动时间>   ← 防 PID 被系统复用
    service_version=<启动时用的版本>
下次启动先用这三要素精确比对：
  · 对得上 + 版本一致   → 直接复用（不弹窗）
  · 对得上 + 版本已不同 → 问"是否换成记录版本重启"（托盘切版本后正好用上，
                          以前必须"停止并退出 → 再双击"两步，现在启动时问一次即可）
  · 对不上（PID/时间不符）→ 才回退到"孤儿"启发式去问
本程序把自己的服务停掉时会清掉该记录，不留失效 PID。

实测（对真实在跑的 3080 服务做三种场景仿真，只写临时状态文件）：
    场景1 PID+启动时间+版本全对   → is_recorded_service=True  reuse_decision=reuse(recorded)  不弹窗
    场景2 记录版本比服务版本新     → svcrec_version_switch_needed=True  → 问"是否换版本重启"
    场景3 启动时间差 5 秒(PID 复用) → is_recorded_service=False  reuse_decision=ask(replace)
注意：从旧版升级过来的**第一次**启动仍会问一次（旧版没写过服务记录），之后就安静了。

自检新增能力（都只读、不碰你的真实状态）：
    set DSH_LAUNCHER_SELFTEST=1
    set DSH_LAUNCHER_STATE_FILE=%TEMP%\dsh-state-test.txt   ← 可选：把状态文件重定向到
                                                              临时文件，用于验证服务记录逻辑
自检输出新增字段：service_record_pid / is_recorded_service / svcrec_version_switch_needed /
reuse_decision / netstat_listen_pid(3080)；带 STATE_FILE 重定向时还会跑三组断言：
svcrec_match_self（PID+时间对上必须判 True）、svcrec_mismatched_start_rejected（时间差 5 秒
必须判 False）、svcrec_clear_ok（清记录后文件里不再有 service_pid）。


v0.6.5：修掉 8 个实测踩到的坑（重点在"插件不兼容"与"页面打不开"）
------------------------------------------------------------------
背景：插件是按**具体 dsh 版本**声明兼容范围的。2026-09-27 实测踩到：dsh 运行时
0.1.5-rc.3，而 @nanmicoder/dsh-auto-mode 只声明支持到 0.1.5-rc.2，且它链接到
开发检查点 dsh-auto-mode，自带一套 0.1.0-rc.6 的 harness 依赖，
而 session/user-approval 落到 npx 缓存的 0.1.5-rc.3 → "mixed Harness packages"
→ 插件在 profile 装载阶段直接抛异常 → **整个服务起不来**。旧版启动器对此只能
干等 180 秒然后报一句"启动超时"。

1. **启动失败快速判定**：扫描服务器输出，识别
   "plugin tree failed to load / failed to apply loader entry <id> (<插件>)"，
   解析出插件名与装载条目 id，**立即**（不再等满 180 秒）弹出修复询问。
2. **文件级自动禁用插件（不需要 pnpm）**：插件报错里建议的
   `dsh plugin --profile <name> remove <pkg>` 内部依赖 pnpm，而本机没装 pnpm
   （实测报 `'pnpm' 不是内部或外部命令`），照做执行不了。本版直接改 profile 配置：
     - package.json：删掉 dependencies 与 dsh.profile.bundles 里的条目（并清理
       删行后留下的悬空逗号）
     - pnpm-workspace.yaml：删掉含该插件名的行
     - cordis.patch.yml：把该插件贡献的 loader 条目对应的补丁整段注释掉，
       **并保证文件顶层仍是 YAML 数组**（注释后若没有生效行，自动补 `[]`；
       否则 dsh 会报 "must be a top-level YAML array of loader patch entries"
       而直接启动失败 —— 这个坑实测踩过）
     改动前把整份配置备份到 `<profile>\.backup-<时间戳>\`，随时可手工恢复。
   改完自动用记录版本重启服务，用户只需点一次"是"。
3. **插件兼容预检（启动前）**：用 node 按真实解析规则（会跟随 junction/符号
   链接）复刻插件自己的 assertHarnessCompatibility 语义 —— 5 个 harness 包
   （session/tools/llm/permission-presets/user-approval）版本必须一致，且该版本
   要在插件 compatibility.json 的 supportedHosts 里。**同时扫描插件已发布的 lib
   代码，确认它是否真的在加载期做这个断言**：实测 @nanmicoder/dsh-agent-teams
   版本同样混杂，但它不调用断言、能正常加载；只有 auto-mode 这类会抛错的才拦。
   判定分四种：fatal（会让服务起不来，会拦截并询问）/ risky（版本混杂但不校验，
   只在报告里提示）/ ok / unknown。不兼容时问：[是] 禁用并继续 / [否] 仍要试 /
   [取消] 退出。
4. **打开真正能用的地址**：dsh 启动时会打印带 token 的地址，本版把它抓出来用于
   打开浏览器（裸地址可能被 token 校验拒绝，表现为页面打不开 / Failed to fetch）。
5. **半死服务识别**：3080 有 node 进程在监听、但 HTTP 完全不响应时，不再静默复用
   （那正是"重启多少次都还是 Failed to fetch"的来源），而是询问"结束它并按记录
   版本重新启动"。
6. **健康服务不再被误判**：dsh 对无 token 请求返回 401，旧版把 401 当异常 →
   误报"3080 被其他程序占用"。本版把"HTTP 层有响应 + 占用者是 node"视为 dsh。
7. **启动等待响应"停止"**：旧版在启动等待期间点"停止服务并退出"仍要等满 180 秒，
   本版立即收手。
8. **npm 路径全线失效（实测日志暴露）**：本机环境同时存在 `HTTP_PROXY` 与
   `http_proxy`（`HTTPS_PROXY`/`https_proxy` 同理），而 .NET 的
   `ProcessStartInfo.EnvironmentVariables` 是**大小写不敏感**的字典 —— 一访问它就抛
   `已添加项。字典中的关键字:“HTTP_PROXY”所添加的关键字:“http_proxy”`，
   `Process.Start` 直接失败。受影响的正是 StartViaNpx / RunNpmCapture /
   FetchLatestViaNpm —— 也就是 **npx 启动、"检查更新"、可安装性校验、升级下载**
   全部静默失效（日志表现为"可安装性校验 …: 未通过"，于是永远不提示升级）。
   现在所有 npm 开关改用**命令行参数**（`--no-fund --no-update-notifier
   --prefer-offline/--prefer-online`），彻底不碰那个字典；顺带把
   `FetchLatestViaNpm` 里残留的"先 ReadToEnd 再 WaitForExit"（超时形同虚设，
   v0.6.3 漏修的一处）改成统一的安全读取。

另外：本次替换/重启过 3080 上的服务时，跳过"浏览器里已有页面就不再开"的去重逻辑
（旧页面已随服务重启失效），直接打开新地址，并在托盘提示关掉旧标签页。


版本真正切换（v0.6.4 新增，仍有效）
--------------------------------
症结：启动器原本"3080 已有 DeepSeek 服务就直接复用"。如果那个服务是被任务管理器
强杀的旧启动器留下的**孤儿进程**，就没人能停掉它 —— 于是你重启多少次都在跑旧版本，
记录的新版本永远不生效（实测：记录 0.1.5-rc.3，实际一直跑 0.1.0-rc.7）。

现在：
1. 启动时用 `netstat -ano` 找出监听 3080 的 PID，并比对它的启动时间；
2. 若它**早于本程序启动**（即不是本程序启动的服务），弹窗明确告知并询问：
   [是] 结束它并用记录版本重新启动 / [否] 继续复用它；
3. 选择"是"→ `taskkill /F /T`（整棵树）→ 有界等待端口释放（最多 20 秒）→ 按记录版本启动；
4. 托盘新增 **"结束 3080 服务并退出…"**：随时手动接管（结束占用 3080 的服务并退出本
   程序，随后再次双击启动器即按记录版本干净启动）。
5. 自检新增字段：`netstat_listen_pid(3080)` 与 `leftover_service`。

功能
----
1. 双击运行后，后台隐藏启动命令提示符，**直接运行本机已安装的 dsh**
   （调用 npx 缓存里的 dsh.cmd，不经 npx）：
       <npx缓存>\node_modules\.bin\dsh.cmd web --no-open
   - 实测秒级启动（不依赖联网解析，不会"卡住打不开"）；
   - 只有在需要安装/升级某个指定版本时才走 npx 联网安装。
2. 端口就绪后用你自己的默认浏览器打开网页：收藏夹/扩展照常可用，
   无"同步浏览数据/登录"首次运行弹窗，只开一个 DeepSeek 标签页。
3. 停止服务器：
   - 关闭整个浏览器 → 服务器自动停止，托盘图标消失；
   - 只关标签页 → 右键托盘 → "停止服务并退出"（双击图标 = 重开网页）。

- 停止服务并退出


防卡死设计（v0.6.3 重点）
-------------------------
v0.6.2 实测踩到的坑：升级下载跑了 16 分钟，界面既不成功也不失败；根因是
`RunNpmCapture` 先 `ReadToEnd()` 再 `WaitForExit(超时)` —— stdout 不关闭就永远
停在 ReadToEnd，那个 300 秒上限形同虚设；而且超时后只 Kill 了 cmd，npm/node
变成孤儿继续占网占盘、继续占 npx 目录的 concurrency.lock。本版逐条修掉：

1. **超时真生效**：先起后台读线程、再 WaitForExit；超时立即杀**整棵进程树**
   （cmd → npm.cmd → node），并如实报失败（不假装成功）；
2. **安装上限 30 分钟**（旧版 5 分钟，慢网络下 200 MB 依赖要 16 分钟，
   会把成功误判成失败）；
3. **单飞**：同一时刻只允许一个下载安装，重复点"检查更新…"不会再起第二个
   npm 去抢同一个目录锁（实测两次并发下载几乎同时结束，后一次纯白等）；
4. **进度可见**：下载中托盘提示每 15 秒刷新"已 X 分 Y 秒"，看得出是在跑；
5. **可中断**：下载中随时"停止服务并退出"，会连正在跑的 npm 一起收掉
   （不会退出后还在后台偷偷下载）；
6. **已装好就不重复下载**：待升级版本若本机已有可直接启动的检查点，
   启动时直接切过去用，不再白下十几分钟。

    set DSH_LAUNCHER_REPAIR_ID=auto-permission-mode               ← 可省略
结果里会回读修复后的 package.json / cordis.patch.yml，可直接核对。

另有隐藏钩子 DSH_LAUNCHER_AUTOSTOP_MS=<毫秒>：到时自动走"停止 → 退出"整条路径；
DSH_LAUNCHER_PROFILES_ROOT=<目录> 可覆盖 profile 根目录（自检隔离用）。


版本与升级
----------
1. 启动时查 npm latest（先 HTTPS 直查，失败自动用 npm 命令兜底）并做语义化比较；
2. **只询问确实可安装的版本**（先 `npm view @deepseek-ai/dsh@<版本> version` 校验）；
3. 弹窗默认按钮是"否"，回车不会误升级；拒绝后 12 小时内不再问同一版本；
4. 失败**自动回退**：下载或启动失败都保持原版本，"升级失败又打不开"不会发生；
5. 确认过但没装完的版本记入 pending，下次启动继续；若本机其实已装好则直接切换；
6. 想手动切版本：托盘"切换版本（重启生效）"，或直接编辑 version.txt。

首次运行（没有 version.txt 时）：自动探测本机 npx 缓存里已安装的 dsh 版本并记录，
不擅自换版本；旧版留在程序目录的 dsh-version.txt 会自动迁移到 %LOCALAPPDATA% 并删除。

⚠️ 升级提示：dsh 仍是开发者预览版，破坏性变更常见。**升级 dsh 前先确认插件有对应
新版本**——插件是按具体 dsh 版本声明兼容范围的，版本错配会导致服务直接起不来
（v0.6.5 起启动时会自动预检并给出结论，不会再让你对着"启动超时"猜）。
本机若装了 pnpm，也可以用 dsh 原生的插件命令：
    dsh plugin --profile <profile> add|remove <包名>


托盘响应性（v0.6 修复）
----------------------
v0.4/v0.5 在 UI 线程用"DoEvents + 100ms 轮询 + 进程扫描"，右键托盘菜单明显卡顿。
v0.6 起：UI 线程跑真正的消息循环（Application.Run），监视逻辑全部移到后台线程
（300ms 轮询），弹窗与托盘文字从后台线程回投 UI 线程 → 菜单即时响应。
（v0.6 初版曾用 SynchronizationContext 回投，消息循环启动前不可靠，出现过
"点了停止却退不出去"；现改为 UI 线程 System.Windows.Forms.Timer 取队列 +
5 秒看门狗兜底，保证一定能退出。）

常见问题
--------
Q: 启动时提示"检测到会在加载期抛错的插件"？
A: 插件与当前 dsh 版本错配。选"是"会直接改 profile 配置禁用该插件（先备份到
   .backup-<时间戳>），然后继续启动；想恢复就把备份里的文件复制回去，或等插件
   作者更新支持当前 dsh 版本。本机没装 pnpm，所以不能用 `dsh plugin remove`。

Q: 浏览器页面报 Failed to fetch / 一直打不开？
A: 多为 3080 上残留了一个"半死"服务（进程在、不回应）。v0.6.5 会自动识别并询问
   是否结束重启。也可以托盘 →"结束 3080 服务并退出…"，再重新双击启动器。

Q: 双击后提示"服务启动失败或超时"？
A: 多为首次下载依赖慢、网络不通或 3080 被其他程序占用；弹窗附服务报错摘要与日志
   末尾，也可手动运行 npx @deepseek-ai/dsh web。

Q: 托盘"检查更新…"总是说"不可安装"或失败？
A: v0.6.5 已修。旧版是 npm 命令根本没跑起来（本机 HTTP_PROXY/http_proxy 大小写重复
   导致 .NET 环境字典冲突异常），日志里能看到 `npm 查询异常: 已添加项…`。
   若新版仍失败，请把 %LOCALAPPDATA%\DeepSeekLauncher\launcher.log 末尾发出来。

Q: 刚更新了 exe，行为还是旧的？
A: 旧实例仍在运行（互斥锁被占）。托盘 →"停止服务并退出"，或任务管理器结束
   DeepSeek一键启动.exe，再启动新版。

Q: 升级下载要多久？
A: 视网络而定。本机实测 200 MB 依赖（dsh 本体只有 48 KB，其余是 72 个依赖的
   依赖树）在 npmjs 上跑了 **16 分钟**；本版给到 30 分钟上限并显示已用时间。

Q: 服务被任务管理器强杀后怎么办？
A: 启动器无法感知自己被强杀，服务器可能残留。v0.6.5 会把它识别为"无响应的服务"
   并询问是否结束重启；也可手动 taskkill /F /IM node.exe 或重启电脑清理；
   正常退出请用托盘图标。


技术要点（供二次开发参考）
--------------------------
- C# 编译的 Windows 图形程序（/target:winexe），自身无控制台窗口；
  服务器进程 CreateNoWindow + Hidden 启动，输出重定向到日志。
- 服务器输出的每一行都会被解析：抓 `http://127.0.0.1:3080/?token=…`（打开页面用）
  和插件装载失败特征（瞬时判定 + 自动修复）。
- 进程清理统一走 taskkill /F /T /PID（结束整棵树）；只清理本程序启动的实例。
- 托盘图标 NotifyIcon；`切换版本` 子菜单在 DropDownOpening 时重建，内容来自
  npx 缓存扫描（要求该检查点存在 node_modules\.bin\dsh.cmd）。
- 插件判定用 node 探针（%TEMP%\dsh-launcher-plugin-probe.js），按 Node 的真实
  模块解析规则解析（跟随 junction），并扫描插件 lib 代码判断是否有加载期断言。
- 重新编译：
    C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe /nologo ^
      /target:winexe /optimize+ /codepage:65001 /utf8output ^
      /r:System.Windows.Forms.dll /r:System.Drawing.dll ^
      /win32icon:app.ico /resource:app.ico,dsh_app.ico ^
      /win32manifest:app.manifest /out:DeepSeek一键启动-v0.6.5.exe launcher.cs
  或直接双击 build-v065.cmd。
